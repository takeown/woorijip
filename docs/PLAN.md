# 우리집 개발 계획

마지막 수정: 2026-07-22

## 목표

평소에는 수동 폼이나 자연어로 거래를 기록하고, 월말에는 카드 명세서 엑셀을
업로드해 누락과 오류를 보정할 수 있는 부부 전용 비공개 가계부를 만든다.

이 프로젝트는 Kotlin과 Spring Boot를 배우는 목적도 있다. 프레임워크의 복잡한
기능을 추가하기 전에, 백엔드의 선택을 이해하고 테스트할 수 있는 작은 end-to-end
기능을 차례대로 완성한다.

## 제품 범위

- 초기에는 허용된 Google 계정 두 개만 접근한다.
- 두 계정은 하나의 household에 속하며 거래내역을 공유한다.
- 데이터 모델은 여러 부부가 각자의 household를 가질 수 있도록 구성하고, 모든 가계
  데이터는 household 경계로 격리한다.
- 인증 계정은 사용자와 분리해 관리한다. 초기에는 Google 로그인만 제공하고 이후
  Kakao와 Naver 로그인을 같은 사용자에게 연결할 수 있도록 한다.
- 거래는 수동 폼, AI 자연어 입력, 카드 명세서 엑셀 대조를 통해 기록한다.
- AI 채팅은 한 건의 거래 초안을 작성하고 수정·확정·취소하는 흐름만 지원한다.
- 분석 질의 등 지원하지 않는 요청에는 거래 입력만 가능하다고 안내한다.
- AI가 데이터베이스를 직접 변경하지 않는다. 구조화된 초안을 서버에서 검증하고
  사용자가 확인한 뒤 저장한다.
- 명세서 대조는 결정적인 규칙으로 후보를 찾고, 사용자가 확정한 변경만 반영한다.
- 업로드한 원본 명세서 파일은 영구 저장하지 않고 처리 완료 후 폐기한다.
- 첫 번째 클라이언트는 웹이다. 모바일 앱은 나중에 `apps/mobile`로 추가할 수 있다.

## 현재 마일스톤 결정 기록

### 2026-07-12 — 거래내역 vertical slice부터 시작

인증을 첫 번째 기능으로 구현하지 않는다. 데이터베이스 기반 거래 흐름 하나를 먼저
완성하면 OAuth와 보안 설정에 가려지지 않은 상태에서 Spring 핵심 개념을 익히고
즉시 결과를 확인할 수 있다.

### 2026-07-12 — JPA보다 Spring Data JDBC를 먼저 사용

테이블 관계와 SQL 중심 데이터 모델링이 학습 과정에서 드러나도록 Spring Data JDBC를
사용한다. identity map, lazy loading 또는 복잡한 aggregate mapping이 실제로 필요해질
때만 JPA 도입을 다시 검토한다.

### 2026-07-12 — 프로젝트 Codex 설정 대신 저장소 지침 사용

지속적인 개발 규칙은 `AGENTS.md`에 둔다. 현재 저장소에는 별도의 모델, sandbox,
MCP 또는 hook 설정이 필요하지 않으므로 `.codex/config.toml`은 추가하지 않는다.

### 2026-07-12 — 공통 규칙과 앱별 규칙 분리

저장소 전체에 적용되는 작업 방식과 보안 규칙은 루트 `AGENTS.md`에 둔다.
Next.js 전용 규칙은 `apps/web/AGENTS.md`, Kotlin/Spring 전용 규칙은
`apps/api/AGENTS.md`에 두어 중복 없이 작업 경로에 맞는 지침을 적용한다.

### 2026-07-15 — 자동 수집보다 입력과 월말 보정을 우선

Gmail 결제 메일은 도착 시점과 카드사 지원 여부가 일정하지 않고, iOS와 Android의
문자·알림 수집 방식도 다르다. 외부 플랫폼에 의존하는 자동 수집 대신 수동 폼과
AI 자연어 입력으로 평소 거래를 기록하고, 카드 명세서 엑셀 대조로 월말 누락과 오류를
보정한다. Gmail, 문자, 앱 알림 자동 수집은 핵심 마일스톤에서 제외한다.

### 2026-07-15 — AI 채팅을 거래 입력으로 제한

초기 AI 채팅은 한 건의 거래를 구조화하고, 누락된 값을 질문하고, 초안을 수정한 뒤
사용자 확인을 받아 저장하는 기능만 제공한다. 조회나 소비 분석 요청은 처리하지 않고
거래 입력만 지원한다고 안내한다. AI에는 데이터베이스 변경 권한을 주지 않는다.

### 2026-07-15 — 명세서는 자동 반영하지 않고 대조 근거로 사용

엑셀 명세서는 기존 거래와 비교할 월말 기준 자료다. 대조 결과를 자동으로 저장하거나
수정하지 않고 누락, 중복 의심, 불일치 후보를 사용자에게 보여준 뒤 선택한 변경만
반영한다. 초기에는 카드사 또는 파일 형식 하나만 지원한다.

### 2026-07-15 — 웹은 Spring API를 직접 호출

Next.js는 화면과 라우팅을 담당하고 거래 데이터와 비즈니스 규칙은 Spring API가
소유한다. 브라우저의 거래 등록 요청은 Spring API를 직접 호출하며, API는 설정된
origin에만 거래 경로의 CORS를 허용한다. Next.js API Route나 Server Action을 중간
백엔드로 추가하지 않는다.

### 2026-07-15 — PostgreSQL 통합 테스트에 Testcontainers 사용

Repository와 HTTP 통합 테스트는 H2나 개발자 로컬 데이터베이스 대신 일회용
PostgreSQL Testcontainer를 사용한다. 실제 Flyway migration과 PostgreSQL 타입을
검증하고 테스트 간 데이터 오염을 막는다.

### 2026-07-15 — Household를 가계 데이터 격리 경계로 사용

현재는 한 부부만 사용하지만 여러 부부가 각자의 가계부를 가질 수 있도록 household를
가계 데이터의 소유권과 접근 제어 경계로 사용한다. 모든 거래는 household에 속하고,
API는 인증 사용자의 membership으로 household를 결정한다. 클라이언트가 전달한
household 식별자를 그대로 신뢰하지 않는다. 부부는 household 전체 거래를 공유하며
실제 결제자를 기준으로 전체, 본인, 배우자 거래를 나누어 볼 수 있다.

### 2026-07-15 — 사용자와 인증 제공자 계정을 분리

사용자 데이터는 특정 로그인 제공자에 종속시키지 않는다. `auth_identities`에 제공자와
제공자 고유 사용자 ID를 저장하고 두 값의 조합을 고유하게 유지해 내부 사용자와
연결한다. M2에서는 Google 로그인만 구현하고 허용된 두 계정만 첫 household에
연결한다. 이후 Kakao와 Naver 로그인을 같은 구조에 추가하고, 이미 로그인한 사용자가
다른 제공자 계정을 명시적으로 연결할 수 있게 한다. 이메일 일치만으로 계정을 자동
통합하지 않으며, 자체 비밀번호 인증은 실제 요구가 생기기 전까지 구현하지 않는다.

### 2026-07-16 — Spring API가 OAuth 세션을 소유

Google OAuth2 로그인과 세션은 Spring API가 소유한다. 웹은 API의 로그인 경로로
이동하고 이후 요청에 세션 쿠키를 포함한다. 상태 변경 요청은 CSRF 토큰을 먼저 받아
헤더로 전송하며 CSRF 보호를 끄지 않는다. M2의 단일 인스턴스 환경에서는 메모리
세션을 사용하되, 배포 전에 웹과 API를 같은 site의 도메인으로 구성하거나 세션 전달
방식을 다시 검토한다. Vercel과 Railway의 서로 다른 기본 도메인에 의존하면 브라우저의
교차 사이트 쿠키 제한으로 로그인이 불안정할 수 있다.

### 2026-07-16 — 허용 계정 최초 로그인 시 첫 household 구성

검증된 Google 이메일이 환경변수 allowlist에 포함된 경우에만 최초 로그인을 허용한다.
최초 로그인에서 내부 사용자와 인증 계정을 만들고 첫 household를 생성하거나 기존 첫
household에 가입시킨다. 이후 로그인 식별은 이메일이 아니라 Google `sub`를 사용한다.
현재는 한 부부만 사용하는 bootstrap 정책이며, 다른 부부의 가입을 열기 전에는 초대나
관리자 provisioning으로 교체한다.

### 2026-07-21 — Responses API로 거래 초안 생성

Spring API가 OpenAI Responses API를 호출하고 strict JSON Schema로 거래 초안을 받는다.
초기 모델은 비용과 응답 속도를 고려해 `gpt-5.6-luna`를 사용하며 환경변수로 교체할 수
있게 한다. 요청 원문과 응답을 OpenAI에 저장하지 않도록 `store: false`를 사용하고,
reasoning effort와 최대 출력 토큰을 제한한다. 모델 출력은 서버 비즈니스 규칙으로 다시
검증하며 AI는 거래를 직접 저장하지 않는다. 사용자가 초안을 확인한 경우에만 기존 거래
등록 API를 호출한다.

### 2026-07-22 — 누락값 보완 대화는 무상태로 제한

누락된 거래 정보는 브라우저가 최초 입력과 최대 두 번의 추가 답변을 잠시 유지하고,
각 요청에서 전체 사용자 입력을 다시 전달해 보완한다. 서버는 사용자 입력을 최대 세
개로 제한하고 하나의 거래 문맥으로 조합한다. 대화와 AI 질문은 데이터베이스에 저장하지
않으며 Responses API의 `store: false`를 유지한다. 화면에는 현재 AI 요청 횟수를 표시하고
세 번째 응답에서도 초안이 완성되지 않으면 내용을 보완해 처음부터 다시 입력하도록
안내한다.

### 2026-07-22 — 첫 배포는 Lightsail 단일 인스턴스로 구성

초기 사용자는 부부 두 명이므로 AWS Lightsail 2GB 인스턴스 한 대에서 Next.js,
Spring API, PostgreSQL을 Docker Compose로 함께 운영한다. Caddy가 단일 도메인의
HTTPS를 종료하고 웹 요청은 Next.js로, `/api` 요청은 Spring API로 전달한다. 이 구성은
브라우저의 교차 사이트 세션 쿠키 문제를 피하고 월 인프라 비용을 예측 가능하게 한다.
서버에서 빌드해 메모리를 소모하지 않도록 운영 이미지는 GitHub Actions에서 생성한다.
단일 서버 장애로 애플리케이션과 데이터베이스가 함께 영향을 받으므로 Lightsail 자동
스냅샷과 서버 외부 PostgreSQL 논리 백업을 배포 필수 조건으로 둔다. 사용량이나 가용성
요구가 커지면 데이터베이스와 애플리케이션을 분리한다.

### 2026-07-22 — 첫 Lightsail 운영 배포 검증

Lightsail 2GB 인스턴스에서 PostgreSQL, Spring API, Next.js, Caddy를 Docker
Compose로 실행했다. `main` CI 성공 후 GHCR에 게시한 commit SHA 이미지를
`Deploy production` workflow로 배포했고, 컨테이너 healthcheck, HTTPS,
Google 로그인, 수동 거래 등록·조회를 확인했다. AWS 월별 비용 예산과
이메일 알림도 설정했다.

고정 IP가 없는 GitHub-hosted runner의 배포를 위해 GitHub OIDC로 AWS 단기 자격
증명을 발급한다. workflow가 runner 공인 IPv4의 `/32`만 22/TCP에 임시 추가하고
성공·실패와 관계없이 같은 규칙을 제거한다. IAM 신뢰 정책은 production Environment로,
역할 권한은 운영 Lightsail 인스턴스의 방화벽 개방·폐쇄 작업으로 제한한다.
실제 운영 배포에서 OIDC 인증, 임시 규칙 추가, SSH 배포, 임시 규칙 제거와 외부 HTTPS
응답을 확인했다. AWS 역할 ARN, 리전, 인스턴스 이름은 GitHub production Environment의
Secret이 아니라 Variable로 관리한다.
외부 논리 백업과 복구 검증이 완료되기 전까지 단일 서버 장애에 대한 데이터
복구 위험은 남아 있다.
