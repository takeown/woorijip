MCP 또는 hook 설정이 필요하지 않으므로 `.codex/config.toml`은 추가하지 않는다.

### 2026-07-12 — 공통 규칙과 앱별 규칙 분리

저장소 전체에 적용되는 작업 방식과 보안 규칙은 루트 `AGENTS.md`에 둔다.

`apps/api/AGENTS.md`에 두어 중복 없이 작업 경로에 맞는 지침을 적용한다.

### 2026-07-15 — 자동 수집보다 입력과 월말 보정을 우선

Gmail 결제 메일은 도착 시점과 카드사 지원 여부가 일정하지 않고, iOS와 Android의
문자·알림 수집 방식도 다르다. 외부 플랫폼에 의존하는 자동 수집 대신 수동 폼과
AI 자연어 입력으로 평소 거래를 기록하고, 카드 명세서 엑셀 대조로 월말 누락과 오류를
보정한다. Gmail, 문자, 앱 알림 자동 수집은 핵심 마일스톤에서 제외한다.

### 2026-07-15 — AI 채팅을 거래 입력으로 제한

초기 AI 채팅은 한 건의 거래를 구조화하고, 누락된 값을 질문하고, 초안을 수정한 뒤
사용자 확인을 받아 저장하는 기능만 제공한다. 조회나 소비 분석 요청은 처리하지 않고
거래 입력만 지원한다고 안내한다. AI에는 데이터베이스 변경 권한을 주지 않는다.

### 2026-07-15 — 명세서는 자동 반영하지 않고 대조 근거로 사용

엑셀 명세서는 기존 거래와 비교할 월말 기준 자료다. 대조 결과를 자동으로 저장하거나
수정하지 않고 누락, 중복 의심, 불일치 후보를 사용자에게 보여준 뒤 선택한 변경만
반영한다. 초기에는 카드사 또는 파일 형식 하나만 지원한다.

### 2026-07-15 — 웹은 Spring API를 직접 호출

Next.js는 화면과 라우팅을 담당하고 거래 데이터와 비즈니스 규칙은 Spring API가
소유한다. 브라우저의 거래 등록 요청은 Spring API를 직접 호출하며, API는 설정된
origin에만 거래 경로의 CORS를 허용한다. Next.js API Route나 Server Action을 중간
백엔드로 추가하지 않는다.

### 2026-07-15 — PostgreSQL 통합 테스트에 Testcontainers 사용

Repository와 HTTP 통합 테스트는 H2나 개발자 로컬 데이터베이스 대신 일회용
PostgreSQL Testcontainer를 사용한다. 실제 Flyway migration과 PostgreSQL 타입을
검증하고 테스트 간 데이터 오염을 막는다.

### 2026-07-15 — Household를 가계 데이터 격리 경계로 사용

현재는 한 부부만 사용하지만 여러 부부가 각자의 가계부를 가질 수 있도록 household를
가계 데이터의 소유권과 접근 제어 경계로 사용한다. 모든 거래는 household에 속하고,
API는 인증 사용자의 membership으로 household를 결정한다. 클라이언트가 전달한
household 식별자를 그대로 신뢰하지 않는다. 부부는 household 전체 거래를 공유하며
실제 결제자를 기준으로 전체, 본인, 배우자 거래를 나누어 볼 수 있다.

### 2026-07-15 — 사용자와 인증 제공자 계정을 분리

사용자 데이터는 특정 로그인 제공자에 종속시키지 않는다. `auth_identities`에 제공자와
제공자 고유 사용자 ID를 저장하고 두 값의 조합을 고유하게 유지해 내부 사용자와
연결한다. M2에서는 Google 로그인만 구현하고 허용된 두 계정만 첫 household에
연결한다. 이후 Kakao와 Naver 로그인을 같은 구조에 추가하고, 이미 로그인한 사용자가
다른 제공자 계정을 명시적으로 연결할 수 있게 한다. 이메일 일치만으로 계정을 자동
통합하지 않으며, 자체 비밀번호 인증은 실제 요구가 생기기 전까지 구현하지 않는다.

### 2026-07-16 — Spring API가 OAuth 세션을 소유

Google OAuth2 로그인과 세션은 Spring API가 소유한다. 웹은 API의 로그인 경로로
이동하고 이후 요청에 세션 쿠키를 포함한다. 상태 변경 요청은 CSRF 토큰을 먼저 받아
헤더로 전송하며 CSRF 보호를 끄지 않는다. M2의 단일 인스턴스 환경에서는 메모리
세션을 사용하되, 배포 전에 웹과 API를 같은 site의 도메인으로 구성하거나 세션 전달
방식을 다시 검토한다. Vercel과 Railway의 서로 다른 기본 도메인에 의존하면 브라우저의
교차 사이트 쿠키 제한으로 로그인이 불안정할 수 있다.

### 2026-07-23 — 로그인 세션을 PostgreSQL에 30일간 유지

기본 메모리 세션은 30분 비활성 만료, 브라우저 종료, API 컨테이너 재시작과 배포 시
로그인이 풀린다. Spring Session JDBC로 세션을 PostgreSQL에 저장하고 세션 timeout과
브라우저 쿠키 만료를 30일로 맞춘다. 운영 쿠키는 `Secure`, `HttpOnly`, `SameSite=Lax`로
제한하며 명시적인 로그아웃과 30일 비활성 만료 시 세션을 폐기한다. 세션 스키마는
Spring의 자동 초기화가 아니라 Flyway migration으로 관리한다. OAuth 실패는 허용되지
않은 계정, 인증 실패, 로그인 세션 만료로 구분해 웹에 안내한다. 기존 세션도 요청마다
현재 allowlist를 검사하고 제거된 계정이면 즉시 세션을 무효화한다.

### 2026-07-16 — 허용 계정 최초 로그인 시 첫 household 구성

검증된 Google 이메일이 환경변수 allowlist에 포함된 경우에만 최초 로그인을 허용한다.
최초 로그인에서 내부 사용자와 인증 계정을 만들고 첫 household를 생성하거나 기존 첫
household에 가입시킨다. 이후 로그인 식별은 이메일이 아니라 Google `sub`를 사용한다.
현재는 한 부부만 사용하는 bootstrap 정책이며, 다른 부부의 가입을 열기 전에는 초대나
관리자 provisioning으로 교체한다.

### 2026-07-21 — Responses API로 거래 초안 생성

Spring API가 OpenAI Responses API를 호출하고 strict JSON Schema로 거래 초안을 받는다.
초기 모델은 비용과 응답 속도를 고려해 `gpt-5.6-luna`를 사용하며 환경변수로 교체할 수
있게 한다. 요청 원문과 응답을 OpenAI에 저장하지 않도록 `store: false`를 사용하고,
reasoning effort와 최대 출력 토큰을 제한한다. 모델 출력은 서버 비즈니스 규칙으로 다시
검증하며 AI는 거래를 직접 저장하지 않는다. 사용자가 초안을 확인한 경우에만 기존 거래
등록 API를 호출한다.

### 2026-07-22 — 누락값 보완 대화는 무상태로 제한

누락된 거래 정보는 브라우저가 최초 입력과 최대 두 번의 추가 답변을 잠시 유지하고,
각 요청에서 전체 사용자 입력을 다시 전달해 보완한다. 서버는 사용자 입력을 최대 세
개로 제한하고 하나의 거래 문맥으로 조합한다. 대화와 AI 질문은 데이터베이스에 저장하지
않으며 Responses API의 `store: false`를 유지한다. 화면에는 현재 AI 요청 횟수를 표시하고
세 번째 응답에서도 초안이 완성되지 않으면 내용을 보완해 처음부터 다시 입력하도록
안내한다.

### 2026-07-22 — 첫 배포는 Lightsail 단일 인스턴스로 구성

초기 사용자는 부부 두 명이므로 AWS Lightsail 2GB 인스턴스 한 대에서 Next.js,
Spring API, PostgreSQL을 Docker Compose로 함께 운영한다. Caddy가 단일 도메인의
HTTPS를 종료하고 웹 요청은 Next.js로, `/api` 요청은 Spring API로 전달한다. 이 구성은
브라우저의 교차 사이트 세션 쿠키 문제를 피하고 월 인프라 비용을 예측 가능하게 한다.
서버에서 빌드해 메모리를 소모하지 않도록 운영 이미지는 GitHub Actions에서 생성한다.
단일 서버 장애로 애플리케이션과 데이터베이스가 함께 영향을 받으므로 Lightsail 자동
스냅샷과 서버 외부 PostgreSQL 논리 백업을 배포 필수 조건으로 둔다. 사용량이나 가용성
요구가 커지면 데이터베이스와 애플리케이션을 분리한다.

### 2026-07-22 — 첫 Lightsail 운영 배포 검증

Lightsail 2GB 인스턴스에서 PostgreSQL, Spring API, Next.js, Caddy를 Docker
Compose로 실행했다. `main` CI 성공 후 GHCR에 게시한 commit SHA 이미지를
`Deploy production` workflow로 배포했고, 컨테이너 healthcheck, HTTPS,
Google 로그인, 수동 거래 등록·조회를 확인했다. AWS 월별 비용 예산과
이메일 알림도 설정했다.

고정 IP가 없는 GitHub-hosted runner의 배포를 위해 GitHub OIDC로 AWS 단기 자격
증명을 발급한다. workflow가 runner 공인 IPv4의 `/32`만 22/TCP에 임시 추가하고
성공·실패와 관계없이 같은 규칙을 제거한다. IAM 신뢰 정책은 production Environment로,
역할 권한은 운영 Lightsail 인스턴스의 방화벽 개방·폐쇄 작업으로 제한한다.
실제 운영 배포에서 OIDC 인증, 임시 규칙 추가, SSH 배포, 임시 규칙 제거와 외부 HTTPS
응답을 확인했다. AWS 역할 ARN, 리전, 인스턴스 이름은 GitHub production Environment의
Secret이 아니라 Variable로 관리한다.
외부 논리 백업과 복구 검증이 완료되기 전까지 단일 서버 장애에 대한 데이터
복구 위험은 남아 있다.

### 2026-07-23 — CI 병렬화와 수동 운영 릴리스

웹과 API의 CI 검증 및 Docker 이미지 빌드는 서로 독립된 job으로 병렬 실행한다.
모든 `main` push에서 코드 검증은 계속 실행하되, 비용이 큰 이미지 게시는 운영 배포가
필요할 때 `Release production`을 수동으로 실행한다. 이 workflow는 웹과 API 이미지를
병렬 게시한 뒤 동일 commit SHA를 Lightsail에 배포한다. `Publish images`와
`Deploy production`은 이미지 단독 게시와 기존 이미지 rollback을 위해 개별 실행도
유지한다. 변경 경로에 따른 job 생략과 웹·API 독립 배포는 호환성 및 배포 상태 관리가
필요해 이번 범위에서 도입하지 않는다. GitHub-hosted runner는 운영 호스트 버전과의
일치가 아니라 CI 환경의 예측 가능성을 위해 `ubuntu-24.04`로 고정한다.

### 2026-07-23 — 거래에 결제수단과 카드사 기록

수동 입력과 AI 입력에서 카드 또는 현금을 필수로 기록한다. 카드 결제는
여신금융협회 통계 기준 국내 카드사 9곳(롯데, BC, 삼성, 신한, 우리, 하나, 현대,
KB국민, NH농협) 중 하나를 선택하고, 현금 결제는 카드사를 기록하지 않는다. 운영에
이미 저장된 거래는 결제수단을 추측하지 않고 `UNKNOWN`으로 보존하되 신규 거래에서는
`UNKNOWN`을 허용하지 않는다. 이 정보는 이후 카드 명세서 대조의 기준으로 사용한다.

### 2026-07-24 — 거래에 선택 내역 기록

가맹점은 결제처와 카드 명세서 대조 기준으로 유지하고, 구매 품목이나 사용 목적은
별도의 선택 `description` 필드에 기록한다. 수동 입력에서는 사용자가 직접 작성하고
AI 입력에서는 사용자가 말한 내용만 추출한다. 내역이 없다는 이유로 AI가 추가 질문하지
않으며 기존 거래와 향후 명세서 거래는 내역 없이도 저장할 수 있다.

### 2026-07-26 — 카드 명세서 대조보다 기간별 통계를 먼저 제공

실제 사용에서 수동 거래 입력이 빠르게 정착했으므로, 월말 누락 보정보다 축적된 기록의
효용을 매일 확인할 수 있는 일·주·월 지출 통계를 먼저 구현한다. 첫 통계는 결정적인
데이터베이스 집계로 총액, 거래 건수, 이전 기간 비교, 결제자·결제수단·현재 카테고리
구성을 제공하고 AI 설명은 포함하지 않는다. 현재 카테고리는 자유 입력이라 같은 성격의
지출이 여러 이름으로 나뉠 수 있음을 화면에서 감안하며, 표준 분류와 태그 기반의 정교한
비교는 분류 마일스톤 이후로 미룬다. 카드 명세서 엑셀 대조는 기간별 통계 다음
마일스톤으로 순서를 변경한다.

### 2026-07-26 — 기간 경계와 household 통계 집계는 API가 소유

클라이언트는 기간 종류와 기준 날짜만 전달하고, Spring API가 `Asia/Seoul` 기준의
일·주·월 시작과 종료 및 이전 비교 기간을 계산한다. 주간은 월요일부터 일요일까지로
정의한다. 클라이언트가 household 식별자를 전달하지 않으며 API는 인증 사용자의
household로 모든 집계를 제한한다. 통계는 기존 `transactions` 테이블과
`household_id`, `occurred_at` 복합 인덱스를 사용하는 명시적인 JDBC 집계 쿼리로
계산하므로 별도 집계 테이블이나 Flyway migration을 추가하지 않는다.
사람별 통계 필터도 임의의 사용자 ID 대신 `all`, `me`, `partner`만 받고, API가
household membership을 사용해 실제 결제자를 결정한다.

### 2026-07-26 — 거래와 통계 화면을 별도 라우트로 분리

거래 입력과 최근 거래내역은 루트 `/`에 유지하고 기간별 통계는 `/stats`에서
제공한다. 공통 클라이언트 shell이 로그인 확인, 로그아웃, 거래·통계 내비게이션을
담당해 인증 로직을 중복하지 않는다. 각 라우트는 자신에게 필요한 데이터만 요청하며,
거래 화면은 통계 상태를 직접 관리하지 않는다.

### 2026-07-27 — 카드사별 명세서를 공통 거래 후보로 정규화

첫 지원 형식은 KB국민카드 이용대금명세서 XLSX로 확정하고 전체 업로드·대조 흐름을
먼저 완성한다. 현대카드가 XLS 확장자의 HTML 표를 제공하는 것처럼 카드사마다 파일
구조가 다르므로 카드사별 parser가 형식 감지와 행 해석을 담당하고, 이후 대조와 사용자
검토는 공통 명세서 항목 모델만 사용한다. KB국민카드 흐름을 검증한 뒤 같은 공통
모델에 현대카드 parser를 추가한다.

공통 명세서 항목은 승인 금액과 이번 달 청구 금액을 구분하고 승인, 취소, 할인,
연회비, 할부 유형을 명시한다. 소계와 합계는 거래로 만들지 않고 파일 전체의 건수와
청구 금액을 검증하는 근거로만 사용한다. 일치한 거래는 요약하고 누락, 중복 의심,
불일치처럼 판단이 필요한 항목만 기본 검토 대상으로 보여준다.

업로드 원본은 영구 저장하거나 로그에 남기지 않는다. 재업로드 중복 방지에는 카드사,
명세서 월, 정규화된 항목으로 만든 결정적인 fingerprint를 사용하고, 사용자가 확정한
항목만 기존 `transactions`에 반영한다. 지출 통계는 명세서 항목이 아니라 확정된
`transactions`를 계속 단일 기준으로 사용한다.

원본 파일 대신 정규화된 명세서 가져오기와 거래 후보만 저장한다. 논리 내용의
SHA-256 fingerprint가 같은 재업로드는 기존 가져오기를 재사용한다. 사용자가 누락
후보를 선택하면 저장 직전에 대조를 다시 수행하고, 여전히 누락인 항목만 거래로
생성한 뒤 후보에 생성된 거래 ID를 연결한다. 이미 연결된 후보의 재적용은 기존 거래
ID를 반환해 중복 생성을 막는다. 명세서는 이용 시각을 제공하지 않으므로 생성 거래는
해당 이용일의 `Asia/Seoul` 정오로 기록하고 승인 금액을 거래 금액으로 사용한다.
단일 불일치 후보를 사용자가 선택하면 명세서의 가맹점과 승인 금액만 기존 거래에
반영한다. 카테고리, 내역, 결제 시각과 생성 시각은 보존한다. 사용자가 미리보기에서
확인한 기존 가맹점과 금액이 적용 전에 달라졌다면 조건부 갱신을 거부하고 다시
대조하도록 안내해 다른 수정 내용을 덮어쓰지 않는다.

초기 대조는 업로드한 로그인 사용자를 카드 결제자로 간주하고 같은 household의 해당
사용자 거래만 조회한다. `Asia/Seoul` 이용일, 카드사, 승인 금액, 공백과 기호를 제거한
가맹점명이 모두 같으면 일치로 판단한다. 같은 날짜와 금액에서 가맹점명이 포함 관계인
경우도 단일 후보일 때만 일치로 처리한다. 날짜가 같고 금액 또는 가맹점만 맞으면
불일치, 가능한 기존 거래가 여러 개면 중복 의심, 없으면 누락으로 분류한다. 동일한
날짜·금액·가맹점 거래가 여러 건이면 파일과 데이터베이스의 발생 횟수를 일대일로
소진해 정상 반복 결제를 중복으로 오인하지 않는다.

웹의 `/statements`를 거래 입력과 통계에서 분리된 월말 보정 화면으로 사용한다. 기본
목록은 일치 항목을 접고 누락, 중복 의심, 불일치만 보여준다. 현재 API가 안전하게
반영할 수 있는 누락 항목에는 선택과 카테고리·내역 입력을 제공한다. 단일 불일치는
현재 거래와 명세서 기준을 나란히 보여주고 가맹점·금액 수정 여부를 선택하게 한다.
여러 기존 거래가 연결된 중복 의심은 자동 변경하지 않고 확인 대상으로만 표시한다.

### 2026-07-27 — 표준 분류와 추천 우선순위

기본 카테고리는 자유 입력이 아니라 서버가 소유하는 닫힌 상수 집합으로 관리한다.
첫 집합은 식비, 주거, 교통, 생활, 건강, 여가, 교육, 금융·보험, 경조사, 기타로
제한하고 API에는 안정적인 영문 코드를 사용한다. 화면은 코드에 대응하는 한글 이름과
대표 지출 예시를 표시한다. 경계가 헷갈리는 항목은 선택 화면에서 추가 안내를 제공한다.
카테고리는 거래마다 정확히 하나를 선택하고, 구독, 공과금, 정기결제처럼 의미가 겹칠
수 있는 태그는 정해진 목록에서 여러 개를 선택할 수 있게 분리한다.

AI는 서버가 전달한 카테고리와 태그 목록 밖의 값을 만들 수 없고 추천만 담당한다.
수동 입력, AI 초안, 명세서 누락 반영과 거래 수정은 저장 전에 사용자가 카테고리와
태그를 확인하거나 변경할 수 있어야 한다. 사용자가 확정한 분류는 이후 자동 분류가
덮어쓰지 않는다.

새 거래의 추천은 현재 거래에 대한 사용자 확정, household의 명시적인 가맹점 규칙,
같은 정규화 가맹점에 대해 서로 일치하는 과거 사용자 확정 거래, AI 순서로 적용한다.
과거 확정 결과가 서로 충돌하면 이를 결정적 규칙으로 취급하지 않고 AI 추천 또는
사용자 선택으로 넘긴다. AI는 앞선 결정적 근거가 없는 경우에만 호출한다.

자연어 거래 입력에서는 AI가 먼저 가맹점, 내역, 금액, 결제자, 결제수단과 발생 시각을
구조화한다. 분류는 추출된 값에 가맹점 규칙과 과거 확정 거래를 적용한 뒤, 결정적인
근거가 없을 때만 별도 AI 추천을 요청한다. AI 분류 요청에는 필요한 구조화 필드와
허용된 카테고리·태그 목록만 전달하고 정해진 값만 반환하는 스키마로 검증한다.

분류 결과에는 추천 출처, 신뢰도와 사용자 확정 시각을 기록한다. 사용자가 직접
선택하거나 추천을 확인해 저장하면 확정 상태가 되며, 이후 수정은 다시 사용자 확정으로
기록한다. 기존 자유 입력 카테고리는 바로 폐기하지 않고 매핑 가능한 값만 표준
카테고리로 옮긴다. 나머지는 기존 값을 보존한 채 기타로 표시하고 재확정 대상으로 둔다.
가맹점 규칙은 거래 한 건을 확정했다는 이유만으로 자동 생성하지 않고 사용자가
“앞으로 이 가맹점에도 적용”을 명시적으로 선택한 경우에만 저장한다.

거래는 household 경계 안에서만 수정하거나 삭제할 수 있다. 수정은 화면에서 확인한
`updated_at`이 그대로일 때만 전체 입력값과 분류를 갱신해 다른 변경을 덮어쓰지 않는다.
삭제는 사용자 확인을 받은 뒤 hard delete한다. 명세서 후보에 연결된 거래를 삭제하면
후보 자체는 보존하고 거래 연결만 해제해 이후 다시 누락 후보로 검토할 수 있게 한다.

### 2026-07-28 — 오류 응답을 ProblemDetail 하나로 통일

모든 JSON 오류 응답은 RFC 9457 ProblemDetail을 사용하고, `status`와 별개로 안정적인
기계 판독용 `code`를 함께 반환한다. `ResponseEntityExceptionHandler`를 상속한 advice
하나가 이를 담당하며, 이 빈이 있으면 Spring Boot의 기본 ProblemDetails 처리는
물러나므로 Bean Validation 실패 같은 프레임워크 예외도 같은 형식으로 나간다.

`code`는 클라이언트가 분기할 의미가 있는 단위로만 정의하고 메시지마다 만들지 않는다.
명세서 오류는 throw 지점이 많으므로 `INVALID_CARD_STATEMENT` 하나로 묶고 구체적인
이유는 `detail`에 남긴다. HTTP status는 이전과 동일하게 유지한다. 웹은 현재 오류
본문을 읽지 않고 status로만 분기하므로 `code` 활용은 필요해질 때 웹에서 따로 도입한다.

Spring Security 필터에서 직접 나가는 인증 실패 응답은 이 advice를 거치지 않아 `code`가
없다. 웹이 401을 status로만 처리하는 동안은 그대로 둔다.

Controller가 반복하던 인증 사용자 조회는 `CurrentUser` 파라미터를 해석하는
`HandlerMethodArgumentResolver`로 옮긴다. 허용 계정이지만 내부 사용자가 없는 경우는
이전과 같은 인증 예외를 던져 401을 유지한다.

외부 OpenAI 호출에는 연결 5초, 읽기 30초 타임아웃을 둔다. 단일 인스턴스 운영이라
응답하지 않는 호출이 요청 스레드를 무기한 점유하면 안 된다. Spring Boot 4에서 RestClient
자동 구성은 별도 모듈로 분리돼 이 프로젝트 클래스패스에 없으므로, 타임아웃은 직접
구성한 `RestClient.Builder`에 설정한다.

### 2026-07-28 — 명시적으로 저장한 가맹점 분류 규칙부터 적용

수동 거래를 저장할 때 사용자가 “앞으로 이 가맹점에도 적용”을 선택한 경우에만 현재
카테고리와 태그를 household 가맹점 규칙으로 저장한다. 가맹점은 NFKC 정규화 후
대소문자, 공백과 기호를 제거한 값으로 정확히 일치시키며 포함 관계는 규칙 오적용을
막기 위해 사용하지 않는다.

수동 입력 화면은 가맹점 입력을 마치면 현재 household의 규칙을 조회해 카테고리와
태그를 채운다. 추천 규칙 ID와 가맹점·카테고리·태그가 저장 시점에도 일치할 때만
서버가 분류 출처를 `MERCHANT_RULE`로 기록한다. 사용자가 추천을 수정하면 규칙 ID를
제거해 사용자 분류로 저장한다. 기존 거래 보완, 과거 확정 이력 추천과 AI fallback은
후속 vertical slice로 남긴다.

### 2026-07-29 — 가맹점 규칙으로 재확정 대상 거래 보완

사용자가 가맹점 규칙을 명시적으로 저장하면 같은 household에서 정규화 가맹점이
정확히 일치하는 재확정 대상 `MIGRATION` 거래만 규칙의 카테고리와 태그로 보완한다.
V8에서 표준 카테고리로 정상 변환된 과거 사용자 입력은 보존하고, 표준 목록에 없던
기존 카테고리가 `OTHER`로 변환된 거래만 재확정 대상으로 본다. `USER`, `AI`,
`HISTORY` 출처와 사용자가 확인한 `MERCHANT_RULE` 거래는 변경하지 않는다.

보완된 거래는 출처를 `MERCHANT_RULE`, 신뢰도를 `HIGH`로 기록하되 사용자 확인 시각은
`null`로 둔다. 같은 규칙이 변경되면 이 미확정 자동 보완 결과만 새 카테고리와 태그로
다시 동기화한다. 후보 조회 후 다른 요청이 거래를 수정했으면 `updated_at` 조건부
갱신이 실패하고 태그도 변경하지 않는다. 규칙 저장, 거래 분류 갱신과 태그 교체는
같은 transaction에서 처리한다.

### 2026-07-30 — 외부 AI 요청은 데이터 최소화 경계로 관리

OpenAI의 데이터 공유 설정과 관계없이 외부 AI 요청을 별도의 보안 경계로 취급한다.
프롬프트 안내가 아니라 외부 요청 직전의 서버 검사로 금지 데이터를 차단하고, 외부
서비스에 필요한 안정적인 사용자 식별자는 원본 ID 대신 HMAC으로 가명화한다. 구체적인
허용 필드, 금지 데이터, 저장과 검증 기준은 `docs/SECURITY.md`가 소유한다.

### 2026-07-30 — 자동 분류 추천보다 거래내역 페이지네이션을 우선

표준 카테고리와 태그, 명시적인 가맹점 규칙, 거래 수정·삭제까지 실제 사용에 필요한
분류 기반은 마련됐다. 과거 확정 이력과 AI를 사용하는 추가 추천은 사용 패턴이 더
쌓인 뒤 효용을 확인하고 구현하도록 백로그로 옮긴다.

현재 거래 목록 API는 household의 모든 거래와 태그를 한 번에 조회하므로 기록이
쌓일수록 응답 크기와 화면 처리량이 계속 증가한다. 가계 분석에서 답변 근거 거래를
제시할 때도 제한된 거래 조회가 필요하므로 분석보다 먼저 거래내역 페이지네이션을
구현한다. 새 거래가 첫 페이지에 추가돼도 offset 방식의 중복과 누락을 피하도록 현재
정렬인 `occurred_at DESC, id DESC`를 그대로 사용하는 커서 방식을 선택한다. 첫 화면은
20건을 조회하고 클라이언트가 요청할 수 있는 최대 크기는 100건으로 제한한다.

### 2026-07-30 — 명시적 분류와 태그 비교부터 가계 분석 시작

M7의 첫 vertical slice는 기존 지출 통계에 표준 카테고리와 태그별 현재·이전 기간
금액, 거래 건수와 증감률을 추가한다. 이전 기간에만 존재하는 항목도 비교 결과에 남겨
사라진 지출을 확인할 수 있게 하고, household와 결제자 필터는 전체 합계와 동일하게
적용한다.

태그는 한 거래에 여러 개가 붙을 수 있으므로 태그별 금액을 총지출로 합산하지 않고
중복 집계될 수 있음을 화면에 안내한다. 이 단계의 반복 지출은 사용자가 확정한 `구독`,
`공과금`, `정기결제` 태그를 뜻하며, 가맹점과 금액 패턴을 이용한 자동 반복 지출 감지는
백로그로 유지한다.

### 2026-07-30 — 반복 지출 변화는 확정 태그로 결정적으로 설명

반복 지출 변화 설명은 외부 AI를 호출하지 않고 사용자가 확정한 `구독`, `공과금`,
`정기결제` 태그의 현재·이전 기간 집계에서 생성한다. `생활` 카테고리는 장보기처럼
반복성이 보장되지 않는 거래도 포함하므로 설명 대상에 자동으로 포함하지 않는다.

신규, 증가, 감소, 종료를 금액 변화로 구분하고 변화가 없는 항목은 제외한다. 변화의
절대 금액이 큰 순서로 최대 세 개를 보여주며, 태그가 겹칠 수 있으므로 원인이나 반복
지출 총액을 단정하지 않는다. API는 태그, 변화 종류, 금액과 설명 문장을 구조화해
반환하여 이후 근거 거래 연결에도 사용할 수 있게 한다.

### 2026-07-30 — 실행 지침과 기준 문서 소유권 분리

항상 적용해야 하는 짧은 작업 규칙은 `AGENTS.md`에 유지한다. 현재 작업 범위는
`docs/PLAN.md`, 완료한 마일스톤은 `docs/MILESTONES_ARCHIVE.md`, 제품·기술 결정의
배경은 이 문서가 소유한다. 보안 정책과 검증 기준은 `docs/SECURITY.md`를 단일 기준으로
사용하고, `docs/ARCHITECTURE.md`와 `docs/DEPLOYMENT.md`는 실제 구현 흐름과 운영
절차만 설명한다. 작업 경로에 따라 필요한 문서만 읽도록 앱별 `AGENTS.md`에서
조건부로 안내한다.

### 2026-08-03 — 상품권과 바우처를 거래별 할인 대신 별도 잔액으로 관리

육아용품은 기본 분류 `CHILDCARE`로 기록하고 부부 생활비 집계에서 제외한다.
온누리상품권과 임산부 바우처는 거래에 할인액을 직접 기록하는 재원이 아니라 household
범위 안에서 각 구성원이 소유한 별도 잔액 계정으로 관리한다. 온누리 10,000원 충전에
계좌에서 9,300원이 나갔다면
충전 잔액 10,000원과 실제 출금 9,300원을 한 변동에 함께 기록하며 충전 자체는 소비로
집계하지 않는다. 임산부 바우처 지급은 같은 구조에서 실제 출금 0원인 잔액 증가다.

가맹점 소비는 기존 `transactions.amount`에 액면 금액을 기록하고 선택한 잔액 계정에 같은
금액의 `SPEND` 변동을 연결한다. 등록 카드 사용은 `CARD`와 카드사를, QR 사용은 `QR`을
결제 경로로 유지한다. 잔액이 부족하면 거래 저장을 거부하며 거래 생성·수정·삭제와 잔액
변동은 같은 데이터베이스 transaction에서 처리한다.

할인율이 다른 충전 잔액이 섞일 때 구매별 실제 원가를 계산하려면 FIFO 또는 가중평균 같은
원가배분 정책이 필요하므로 첫 구현에서는 `2,400원 소비 = 우리 돈 2,232원`처럼 구매별
원가를 추정하지 않는다. 소비액, 현재 잔액, 충전 액면액과 실제 출금액을 각각 보존한다.

현대카드 명세서의 `가맹점 2,400원`과 `온누리상품권사용(청구할인) -2,400원`은 하나의
소비와 그 결제 근거로 해석한다. 조정 행을 별도 지출로 만들지 않는다. 현대카드가 제공한
원본은 확장자가 `.xls`이지만 실제 내용은 UTF-8 HTML 표다. 확장자나 Content-Type 대신
HTML 구조, 명세서 제목과 10개 필수 열을 검사한다. 온누리 조정 행은 같은 날짜·카드이고
금액이 일치하며 결제원금이 0원인 구매행 바로 다음에 있을 때만 연결한다. 조건이 맞지 않으면
임의로 연결하지 않고 파일 전체를 거부한다.

AI 자연어 초안도 같은 분리를 따른다. `paymentMethod`는 카드·현금·QR 결제 경로를,
`storedValueAccountType`은 온누리상품권·임산부 바우처 잔액 유형을 표현한다. 외부 AI가
household 내부 계정 ID를 선택하게 하지 않고 유형만 반환하게 하며, 웹이 인증된 household의
계정 목록에서 실제 `storedValueAccountId`를 찾아 사용자가 확인할 초안에 채운다.
기본 선택은 AI가 판단한 결제자와 같은 사용자가 소유한 잔액 계정이지만, 결제자와 잔액
소유자는 서로 다른 필드로 유지해 사용자가 확인 단계에서 다른 구성원의 계정을 선택할 수
있게 한다. household 단일 계정으로 생성된 기존 데이터는 V13에서 최초 구성원 소유로
귀속하고 다른 구성원의 기본 계정은 빈 잔액으로 생성한다.

### 2026-08-03 — 데이터 모델 문서와 실행 스키마의 역할 분리

`docs/DATA_MODEL.md`는 테이블 관계, 소유권, 금액 의미와 삭제 정책을 사람이 이해하기 위한
기준으로 사용한다. 실제 컬럼 타입, 제약조건과 인덱스의 실행 기준은 Flyway migration으로
유지한다. 모든 SQL 정의를 Markdown에 복제하지 않고 데이터 의미가 달라지는 변경에만
데이터 모델 문서를 함께 갱신해 문서와 실행 스키마의 불필요한 이중 관리를 피한다.

### 2026-08-04 — 잔액 계정은 자동 생성하지 않고 필요한 구성원이 직접 관리

온누리상품권과 임산부 바우처를 모든 household 구성원에게 자동 생성하면 실제 소유하지
않는 계정까지 나타난다. 조회 시 기본 계정을 만드는 동작을 제거하고, 같은 household의
사용자가 소유자·이름·분류를 지정해 필요한 계정만 생성한다. 이름은 자유롭게 입력하며
분류는 상품권, 바우처, 지역화폐, 선불잔액, 기타로 제한해 화면 표시와 기본 동작에 사용한다.

현대카드 온누리 행과 AI의 온누리·임산부 인식은 일반 분류와 다른 책임이므로 nullable
`automation_key`로 분리한다. 한 소유자에게 같은 자동 연동 키의 활성 계정은 하나만 허용하고,
커스텀 계정에는 키를 두지 않는다. 자동 연동 계정이 없으면 명세서 반영 시 먼저 계정을
추가하도록 안내하며 임의로 잔액 계정을 생성하지 않는다.

잔액 계정의 소유자는 생성 후 변경하지 않는다. 사용 이력과 거래 감사 근거를 지우지 않도록
변동이나 연결 거래가 전혀 없는 계정만 실제 삭제하고, 이력이 있는 계정은 보관한다. 보관한
계정은 과거 거래에 표시하고 기존 거래를 같은 계정으로 수정할 수 있지만 새 충전과 새 거래
선택에서는 제외한다. V14는 기존 V13 계정을 그대로 활성 상태로 이전하므로 실제로 소유하지
않는 0원·미사용 계정은 사용자가 화면에서 삭제한다.
